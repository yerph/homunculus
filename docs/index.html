CHAPTER 01 — OVERVIEW

项目概览

homunculus 是一套可自行部署的多渠道 AI companion 系统，支持 Claude Code（CC）模式与模型 API 模式。两种模式能够在网页端切换；在启用同步选项时，同一对话窗口的前情可以衔接。

系统结构

网页版、手机组件、Telegram、Bark、Keepalive 等是不同的入口或可选功能，实际运行还需要各自的配置。

CHAPTER 03 — CONTEXT CONTINUITY

CC / API 上下文衔接

网页设置中的 CC / API context sync 是独立开关，需要自行启用。启用后，API 回合在当前窗口保存并尝试进入 CC Hub 的同步收件箱；API 聊天本身不会额外唤醒 CC。

API 聊天 -- 会话日志 / Hub Inbox
切换 CC 并发送下一条消息 -- 补入尚未同步的前情
Claude Code -- MCP 回复 + JSONL 确认

同步依赖当前会话范围和消息去重机制。只点击切换按钮不会自动触发新的 CC 请求。公开版需要自行配置正在运行的 CC/tmux 会话以及 Bridge 鉴权。

完整的配置说明参见 CC/API 同步文档 / VIEW。

CHAPTER 04 — ROLLING SUMMARY

API 上下文压缩

这是将较早聊天内容概括为文字摘要、供后续 API 请求继续携带的机制，不是文件压缩，也不是 Claude Code 自带的 compaction。

压缩发生的过程

  1. API 回合成功完成并保存后，客户端检查当前会话的 _compressed 标记。
  2. 当未压缩消息达到 24 条时，保留最近 4 条原文，其余较早消息与既有摘要作为压缩输入。
  3. 优先使用 compression: true 的模型，否则在已配置的 Provider 中寻找 DeepSeek、OpenAI 兼容模型等。
  4. 压缩模型生成摘要，成功后追加到 rolling_summary，并标记对应旧消息为已压缩。
  5. 下一轮 API 请求携带摘要和仍未压缩的近期消息。原始聊天消息不会因压缩而直接从界面删除。

关键约束

单条历史消息最多截取 400 字符，合并输入最多 8,000 字符；模型提示摘要目标约 400 英文单词，生成上限 600 tokens。请求失败或返回空摘要时，不标记旧消息已压缩，之后可以重试。

摘要目前是追加式积累，不保证 token 预算始终可控。它与 CC Sync 是两套不同机制，也不会主动改写 Claude Code 的 JSONL 或长期记忆。

CHAPTER 06 — INSTALLATION / 11 STEPS

一步一步安装

以下是依据项目 README 整理的安装流程预览。命令和路径可能需要根据你的操作系统与部署结构调整；正式部署时建议同时核对仓库的 README 原文及 .env.example。

01 / 准备环境

在 Linux 服务器上准备 Node.js 20+、tmux；需要外网访问时还要准备 Nginx 和 HTTPS 证书。Claude Code 仅在 CC 模式使用。

node --version
tmux -V

02 / 克隆项目

git clone https://github.com/yerph/homunculus.git
cd homunculus

03 / 安装依赖

npm --prefix chat-server ci
npm --prefix cc-bridge ci
# 可选手机组件
npm --prefix phone-widget ci

04 / 配置环境变量

cp .env.example .env

用自己的随机密钥和路径替换示例值；不要把 .env 上传到公开仓库。

CHAT_PORT=4500
CHAT_PASSWORD=replace-with-a-long-random-password
BRIDGE_AUTH_TOKEN=replace-with-a-different-random-token
BRIDGE_CLIENT_PORT=3462
BRIDGE_INTERNAL_PORT=3463
BRIDGE_TMUX=cc
BRIDGE_TMUX_USER=your-linux-username
BRIDGE_CC_SESSION_DIR=/absolute/path/to/your/claude/project/transcripts

05 / 设置 CC Profile

根据需要配置自己的 CLAUDE.md。身份设定与回复风格由使用者自行维护，不要将私人对话或身份资料包含在公开仓库。

06 / 配置 Nginx（远程访问时）

参考项目的 Nginx 配置，设置域名、上游服务与证书路径。证书就绪后再启用 HTTPS 配置，并通过 nginx -t 验证语法。

07 / 配置 Telegram（可选）

需要 Telegram 渠道时，再创建 Bot、安装插件并完成配对。不使用 Telegram 则可跳过。

08 / 启动 CC 与网页服务

先在 tmux 启动自己的 Claude Code 会话，随后分别启动 CC Hub 和 chat-server。

tmux new-session -d -s cc 'claude'
tmux ls

# 在不同终端中运行
node --env-file=.env cc-bridge/hub.js
node --env-file=.env chat-server/server.js

还需在 Claude Code MCP 配置中注册 cc-bridge/bridge.js；仅启动 Hub 并不足以让 CC 回复网页。CC Hub 端口应只允许本机访问。

09 / 配置 Keepalive（可选）

如需定时让 CC 主动发送消息，可根据服务器时区配置 cron 等调度方式。

10 / 配置 Bark（可选）

按需要填写自己的 Bark 凭据，用于 iOS 通知；不使用则跳过。

11 / 安装 PWA（可选）

网页服务可配置为手机或电脑桌面应用。需要通过 HTTPS 访问，并依具体浏览器的安装方式操作。

CHAPTER 07 — PERSONALIZATION

自定义与个性化

主题色、聊天窗口、API Provider、CC Profile、图标与 PWA 表现均可进一步个性化。建议先验证基础 API 对话，再连接 CC 模式与上下文同步，最后添加 Telegram、Bark 与 Keepalive 等外围功能。

CHAPTER 08 — DATA & MAINTENANCE

运行数据与维护

部署到公网时，需要使用 HTTPS、强随机密钥、必要的访问限制，并避免公开开放 CC Hub 的内部端口。公开示例的应用层请求鉴权主要使用 CHAT_PASSWORD 与 x-auth-token；若使用 Cookie 登录，需要自己在前置网关集成相应机制。

聊天记录主要存储在 chat-server/data/conversations/ 等数据目录；密钥、私人 JSONL、API 聊天日志与缓存状态都不应提交到公开仓库。备份时同样需要保护私人数据。

CHAPTER 09 — TROUBLESHOOTING

常见问题与排查

网页打不开或显示 502 Bad Gateway

首先检查 chat-server 是否在运行，然后确认 Nginx 的代理端口与 .env 一致；CC 模式还需要查看 Hub 和 MCP Bridge 的连接状态。

sudo tail -f /var/log/nginx/error.log
Telegram 发消息但 CC 没有回复

检查 Claude Code 的 tmux 会话是否还在、插件是否安装并配对成功。

tmux ls
tmux attach -t cc
API 模式是否会消耗额外费用？

API 模式走的是服务商按调用量计费的接口，与 Claude Code 订阅额度分开计算。历史压缩同样可能使用付费 API。

切回 CC 后为什么没有自动出现 API 聊天内容？

CC Sync 必须启用，而且不是仅切换按钮就注入；需在 CC 模式中正常发送下一条消息，才会按会话规则尝试补入待同步前情。

HTTPS 证书异常怎么办？

检查域名 DNS、证书路径和续期状态；先准备证书，再将相应的 HTTPS 配置生效。
